# Provenance Guard

A Flask API that estimates whether a piece of content was made by a person or generated by AI. It handles text (poems, story excerpts, blog posts) and images (via their metadata and the creator's description). Three independent detection signals for text, and two for images, are combined by a weighted ensemble into a confidence score. The result is shown to readers as a plain-language transparency label. Every decision is recorded in a structured audit log, and creators can appeal a classification for human review.

Creators can also earn a "Verified Human Creator" certificate through a live writing check, and an analytics dashboard shows detection patterns, appeal rates, and signal agreement.

The full design spec, including the architecture diagrams and the stretch feature specs, is in [planning.md](planning.md).

## Setup and Running

Requirements: Python 3.10+, a Groq API key.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
echo "GROQ_API_KEY=your-key-here" > .env
python app.py
```

The server runs on `http://localhost:5001`. Port 5000 is the Flask default, but on macOS it is taken by the AirPlay Receiver, which answers every request with `403`. To use a different port: `PORT=5000 python app.py`.

Example requests:

```bash
curl -s -X POST http://localhost:5001/submit -H "Content-Type: application/json" \
  -d '{"text": "The sun dipped below the horizon, painting the sky in hues of amber and rose.", "creator_id": "test-user-1"}'

curl -s -X POST http://localhost:5001/appeal -H "Content-Type: application/json" \
  -d '{"content_id": "PASTE-CONTENT-ID", "creator_reasoning": "I wrote this myself from a personal experience."}'

curl -s http://localhost:5001/log
```

The analytics dashboard is at `http://localhost:5001/dashboard`.

Run the calibration check (prints every signal score and the combined result for all labeled text and image samples):

```bash
python -m tests.run_calibration
```

## Architecture

A text submission is validated, then scored by three independent signals: an LLM classifier, a stylometric analyzer, and a personal voice analyzer. An image submission is scored by a metadata forensics check and an LLM consistency check. The ensemble scorer combines the signal outputs with fixed weights, checks whether the signals' votes conflict, applies uncertainty adjustments, and assigns one of three attributions. The label generator turns that into reader-facing text, and the creator's certificate status is attached next to it. The full decision, including every individual signal score and vote, is saved and appended to the audit log before the response is returned.

An appeal from the creator moves the content to `under_review` and logs the creator's reasoning next to an unchanged copy of the original decision. The original decision is never overwritten.

```
POST /submit (content_type: text)
  -> rate limiter + validation          (raw text)
  -> Signal 1: LLM classifier           (llm ai_probability + reasoning)
  -> Signal 2: Stylometric analyzer     (stylometry ai_probability + sub-scores)
  -> Signal 3: Personal voice analyzer  (voice ai_probability + sub-scores)
  -> Ensemble scorer                    (ai_score, confidence, attribution, votes, adjustments)
  -> Label generator + certificate      (label text, creator_verification)
  -> Storage + audit log                (content row, classification entry)
  -> Response

POST /submit (content_type: image)
  -> rate limiter + validation          (description + metadata)
  -> Image signal 1: metadata forensics (metadata ai_probability + evidence found)
  -> Image signal 2: LLM consistency    (llm ai_probability + reasoning)
  -> Ensemble scorer -> Label generator -> Storage + audit log -> Response

POST /appeal
  -> rate limiter + validation          (content_id, creator_reasoning)
  -> Status update                      (classified -> under_review, appeal row)
  -> Audit log                          (appeal entry with original decision)
  -> Response
```

| Component | File |
|---|---|
| API layer, validation, rate limiting | `app.py` |
| Signal 1: LLM classifier (text and image prompts) | `detection/llm_signal.py` |
| Signal 2: Stylometric analyzer | `detection/stylometry.py` |

## Detection Signals

Each signal returns an `ai_probability` from 0.0 (human) to 1.0 (AI).

### Signal 1: LLM classifier (Groq, `openai/gpt-oss-120b`)

**What it captures:** A holistic judgment of style and content: generic or hedged phrasing, formulaic structure, missing personal detail, emotionally flat tone, and stock AI vocabulary. The model is called at temperature 0 with a JSON response format and returns a probability plus a one-sentence reason, which is stored for reviewers.

**Why I chose it:** It is the only signal that reads meaning. A text can have perfectly human sentence statistics and still read like a press release, and only a language model notices that.

**What it misses:** Its probabilities are opinions, not measured frequencies, and they vary between runs even at temperature 0 (the same AI paragraph scored 0.88 in one run and 0.81 in another). It is biased against formal and non-native English writing, it can be fooled by lightly edited AI text, and it depends on an external service. Its output is clamped to [0.02, 0.98], and if the call fails the signal is marked `unavailable` and the request still completes.

### Signal 2: Stylometric analyzer (local, pure Python)

**What it captures:** Three surface statistics, each mapped to 0-1 (higher = more AI-like) and averaged:

| Sub-metric | Measures | Mapping |
|---|---|---|
| Burstiness | Coefficient of variation of sentence lengths | CV <= 0.25 -> 1.0, CV >= 0.75 -> 0.0 |
| Word length | Mean letters per word | <= 4.2 -> 0.0, >= 5.8 -> 1.0 |
| AI marker vocabulary | Share of words from a fixed list ("furthermore", "stakeholders", "ensure", "transformative", ...) | rate / 0.05, capped at 1.0 |

**Why I chose it:** Language models pick high-probability tokens, which produces evenly sized sentences, a formal register with longer words, and a recognizable set of transitions. People write in bursts, with fragments and short everyday words. This signal is deterministic, free to run, and fully explainable: every score can be traced back to three numbers.

**What it misses:** It cannot see meaning. AI text prompted to sound casual passes easily, and so does any text that avoids the marker words. Formal human writing and poetry with even line lengths look AI-like (see Known Limitations).

### Signal 3: Personal voice analyzer (local, pure Python)

**What it captures:** Evidence that a specific person is talking:

| Sub-metric | Measures | Mapping to human evidence |
|---|---|---|
| First person | Rate of i/me/my/mine/myself/i'm/i've/i'd/i'll | rate / 0.06, capped at 1.0 |
| Informal markers | Rate of contractions, `?`, `!`, `...`, dashes, parentheses, all-caps emphasis, digits | rate / 0.04, capped at 1.0 |
| Lowercase starts | Share of sentences starting lowercase | as is |

`ai_probability = 0.75 * (1 - mean of the three)`.

**Why I chose it:** Neither of the other signals measures voice directly. Before choosing it I measured these features on the labeled samples: first-person rate was 0.000 on every unedited AI sample and 0.073-0.188 on casual human samples, and lowercase sentence starts never appeared in AI text.

**Why it tops out at 0.75:** It is one-sided by design. Personal voice is strong evidence of a human, but missing personal voice is weak evidence of AI, because formal human writing has none either. The signal can pull a score strongly toward human but only mildly toward AI.

**What it misses:** AI text prompted to write in first person with contractions reads as human (the edited AI sample scored 0.39). Formal writing and poetry written in second or third person get no credit.

### Why these three together

They fail in different ways. The LLM reads meaning but is opaque and uncalibrated. Stylometry is transparent but blind to content. Voice catches the personal specifics that both miss, but only in one direction. When all three agree, that is real evidence. When they actively contradict each other, the system treats the conflict as uncertainty instead of letting one signal win.

## Confidence Scoring

### Approach: weighted ensemble with a vote check

```
text:   ai_score = 0.45 * llm + 0.35 * stylometry + 0.20 * voice
image:  ai_score = 0.60 * metadata + 0.40 * llm
```

Each signal also casts a vote: `ai` if its probability is at least 0.60, `human` if at most 0.40, otherwise it abstains. Then, in order:

1. **Signal conflict:** if one signal votes `ai` and another votes `human`, the score is pulled halfway toward 0.5. A confident label therefore requires that no signal actively contradicts it.
2. **Short-text cap:** text under 40 words is clamped to [0.30, 0.70], so it can only be "uncertain". There is too little text for any signal to be trusted.
3. **Unavailable signal:** if a signal fails (for example the Groq call), the remaining weights are renormalized and the score is clamped to [0.30, 0.70]. Partial evidence never produces a confident label.
4. **Insufficient image evidence:** an image with no recognized metadata fields and no description is clamped to [0.30, 0.70].

`confidence = max(ai_score, 1 - ai_score)` is returned alongside `ai_score`: it is how strongly the result leans toward whichever side it is on. The per-signal votes are returned and logged too.

| `ai_score` | Attribution |
|---|---|
| 0.80 - 1.00 | `likely_ai` |
| 0.30 - 0.79 | `uncertain` |
| 0.00 - 0.29 | `likely_human` |

**Why these thresholds:** Wrongly telling readers that a person's work is AI-generated is the more harmful error, so the AI band is narrower than the human band and the uncertain band is the widest. A 0.51 and a 0.95 produce different labels: 0.51 is "Origin unclear", 0.95 is "Likely AI-generated".

**Why these weights:** The LLM captures content-level patterns the others cannot, so it leads. Stylometry separated the samples well in testing, so it gets the second-largest share. Voice gets the smallest weight because it is one-sided by design. For images, metadata leads because it is direct evidence about the file, while the LLM only sees text about the image.

**Why a vote check instead of a fixed gap:** The first version penalized any two signals more than 0.4 apart. With three signals, a vote conflict is a clearer rule: it ignores signals that abstain and only fires when the evidence actively points both ways.

### How I tested whether the scores are meaningful

The labeled samples in `tests/samples.py` are 7 texts (2 clear AI, 2 clear human, 1 formal human, 1 lightly edited AI, 1 short human poem) and 4 images. `tests/run_calibration.py` prints every signal and the combined result, so a bad score can be traced to the signal causing it.

**The first version failed.** All 7 text samples landed in the uncertain band (scores 0.30-0.55). Printing sub-scores separately showed why:

- Lexical diversity (type-token ratio) was 0.86-0.90 for both human and AI text at 30-60 words, so it scored 0.00 on every sample.
- Trigram repetition was 0.00 on everything except the human poem, where the refrain pushed it to 1.00: a false AI signal on exactly the case it was supposed to protect.
- The LLM prompt told it to stay near 0.5 when unsure, so it gave textbook AI text only 0.78.
- The 80-word short-text cap covered every test input, so no confident label was possible.

I replaced the two dead sub-metrics with word length and AI marker vocabulary (picked after measuring candidate metrics on the same samples), added a calibration scale to the LLM prompt, and lowered the short-text cap to 40 words. Then I added the voice signal for the ensemble. Current results:

| Sample | Truth | LLM | Stylometry | Voice | ai_score | Attribution |
|---|---|---|---|---|---|---|
| clear_ai | AI | 0.81 | 0.91 | 0.75 | 0.83 | likely_ai |
| ai_worklife | AI | 0.78 | 0.93 | 0.64 | 0.80 | likely_ai |
| borderline_edited_ai | AI | 0.32 | 0.45 | 0.39 | 0.38 | uncertain (short-text cap) |
| borderline_formal_human | human | 0.78 | 0.66 | 0.75 | 0.73 | uncertain |
| clear_human | human | 0.09 | 0.11 | 0.00 | 0.08 | likely_human |
| human_bike | human | 0.09 | 0.03 | 0.31 | 0.11 | likely_human |
| human_poem | human | 0.09 | 0.33 | 0.38 | 0.30 | uncertain (short-text cap) |

| Image sample | Truth | Metadata | LLM | ai_score | Attribution |
|---|---|---|---|---|---|
| Midjourney software tag | AI | 0.95 | 0.92 | 0.94 | likely_ai |
| Prompt-style description, 1024x1536 | AI | 0.75 | 0.92 | 0.82 | likely_ai |
| Phone photo with full camera EXIF | human | 0.05 | 0.09 | 0.07 | likely_human |
| Stripped metadata, personal description | human | 0.60 | 0.09 | 0.45 | uncertain (signal conflict) |

Clear cases are confident and on the correct side, borderline cases are uncertain, and no human sample reaches the AI band. The stripped-metadata image shows the conflict rule working: metadata leaned AI only because the platform stripped the camera data, the LLM said human, and the result is inconclusive rather than an accusation.

I also checked the scorer on its own against four hand-calculated cases from the spec (for example, LLM 0.90, stylometry 0.10, voice 0.30 produces conflicting votes and a final score of 0.50), and all four matched.

These samples show that the scores vary in the right direction. They do not show that a 0.83 means "83% of such texts are AI". That would need a much larger labeled corpus (see What I Would Change).

## Transparency Labels

The exact text a reader sees for each variant. `{pct}` is a whole-number percentage: `ai_score * 100` for the AI label, `(1 - ai_score) * 100` for the human label.

**Text:**

| Variant | Shown when | Exact label text |
|---|---|---|
| High-confidence AI | `ai_score >= 0.80` | "Likely AI-generated. Our analysis found strong signs that this text was written by an AI tool (estimated {pct}% likelihood). This is an automated estimate, not a final judgment. The creator can appeal this result." |
| High-confidence human | `ai_score < 0.30` | "Likely human-written. Our analysis found strong signs that this text was written by a person (estimated {pct}% likelihood). This is an automated estimate, not a guarantee." |
| Uncertain | `0.30 <= ai_score < 0.80` | "Origin unclear. Our analysis could not confidently tell whether this text was written by a person or an AI tool. Treat this result as inconclusive. The creator can appeal this result." |

**Image:**

| Variant | Shown when | Exact label text |
|---|---|---|
| High-confidence AI | `ai_score >= 0.80` | "Likely AI-generated. Our analysis found strong signs that this image was created with an AI tool (estimated {pct}% likelihood). This is an automated estimate, not a final judgment. The creator can appeal this result." |
| High-confidence human | `ai_score < 0.30` | "Likely human-made. Our analysis found strong signs that this image was captured or created by a person (estimated {pct}% likelihood). This is an automated estimate, not a guarantee." |
| Uncertain | `0.30 <= ai_score < 0.80` | "Origin unclear. Our analysis could not confidently tell whether this image was made by a person or an AI tool. Treat this result as inconclusive. The creator can appeal this result." |

Once a creator appeals, `GET /content/<id>` also returns: "The creator has appealed this result. It is under human review."

For a creator with a valid certificate, this badge text is shown alongside the label: "Verified Human Creator. This creator passed a live writing check on {date}. This confirms they write in their own voice; it does not certify that this specific piece was written without AI."

Design decisions:
- The first two words state the result, for readers who only skim.
- Percentages appear only on confident labels. Showing "54%" on an uncertain result would suggest a precision the system does not have.
- Every label says it is an automated estimate, and the two labels a creator would contest mention the appeal option.
- No technical vocabulary: no "signal", "score", or "classifier".

## Appeals Workflow

1. The creator sends `POST /appeal` with the `content_id` from their submission and `creator_reasoning` (20-2000 characters, so a reviewer has something to evaluate).
2. The system checks that the content exists (404), that `creator_id` matches the submitter if one is provided (403), and that it is not already under review (409, returning the existing `appeal_id`).
3. In one SQLite transaction: an `appeals` row is created as `pending`, the content's status changes from `classified` to `under_review`, and an `appeal` audit entry is written. The status update only succeeds if the content is still `classified`, so two simultaneous appeals cannot both be accepted.
4. The original scores and label are never modified. There is no automated re-classification.

A reviewer opens `GET /appeals?status=pending` and sees, for each appeal:
- the creator's reasoning and certificate status;
- the content type and a 300-character excerpt of the text;
- the original attribution and score;
- **every individual signal score and its vote**;
- the LLM's one-sentence reasoning, and any adjustments applied.

This shows at a glance whether one signal alone drove the decision.

`creator_id` is optional on appeals, so possession of the `content_id` (which is only returned to the submitter) is enough to appeal. With no authentication system this is an identifier check, not a security boundary.

## Rate Limiting

Implemented with Flask-Limiter, keyed on client IP, in-memory storage. Limits are constants at the top of `app.py`:

```python
SUBMIT_LIMIT = "10 per minute;100 per day"
APPEAL_LIMIT = "5 per hour"
CHALLENGE_LIMIT = "3 per hour"
VERIFY_LIMIT = "10 per hour"
READ_LIMIT = "60 per minute"
```

| Endpoint | Limit | Reasoning |
|---|---|---|
| `POST /submit` | 10 per minute, 100 per day | Every submission makes one Groq call, and Groq's free tier caps the whole API key at about 30 requests per minute. 10 per minute per client leaves room for several users at once. A writer checking their own work submits a handful of pieces a day; 100 per day is far above that, but it stops a script from bulk-scraping the detector or probing it hundreds of times to learn how to evade it. |
| `POST /appeal` | 5 per hour | Each appeal costs a human reviewer's time. A creator rarely needs more than one appeal per piece; 5 per hour covers several pieces while preventing one client from flooding the review queue. |
| `POST /certificate/challenge` | 3 per hour | A creator who fails the writing check can retry, but not fast enough to brute-force it by resubmitting variations until one passes. |
| `POST /certificate/verify` | 10 per hour | Each challenge can only be used once anyway; this only stops request floods. |
| `GET` endpoints | 60 per minute | Cheap reads; the limit only prevents abuse. |

## Audit Log

- a UTC timestamp, the content ID, the creator ID, and the content type;
- the attribution, the combined score, and the confidence;
- every individual signal score and vote, any adjustments, and the label shown.

Appeal entries add the creator's reasoning and a full copy of the original decision. Certificate entries record the verification score and signal scores.

## Stretch Features

All four stretch features are implemented. Each was specified in `planning.md` (section "Stretch Features") before it was built.

### 1. Ensemble detection

Three text signals (LLM, stylometry, personal voice) are combined with documented weights (0.45 / 0.35 / 0.20) plus a voting rule. Each signal votes `ai`, `human`, or abstains, and any active conflict pulls the score toward uncertain. Weights, votes, and the reasoning behind each are described in Detection Signals and Confidence Scoring above. Votes are returned in every response and recorded in every audit entry.

### 2. Multi-modal support (images)

`POST /submit` with `"content_type": "image"` accepts the image's embedded metadata and the creator's description. The image file itself is not uploaded; the metadata and description are what the platform already holds for an image.

```bash
curl -s -X POST http://localhost:5001/submit -H "Content-Type: application/json" -d '{
  "content_type": "image", "creator_id": "maya",
  "description": "A lighthouse on a cliff at sunset, dramatic clouds.",
  "metadata": {"width": 1024, "height": 1024, "software": "Midjourney v6"}
}'
```

Two image signals:
- **Metadata forensics** (`detection/image_metadata.py`, rule-based):
  - If any metadata value names an AI generator (Midjourney, DALL-E, Stable Diffusion, Firefly, ComfyUI, and others, matched as whole words), or `digital_source_type` is the IPTC AI-generated value, the score is 0.95.
  - Otherwise it starts at 0.50: each camera field present (make, model, exposure, aperture, ISO, focal length, GPS) lowers it, typical generator sizes (1024x1024, 1024x1536, ...) raise it, and missing all camera data raises it slightly.
- **LLM consistency check:** the same model with an image-specific prompt. It looks for generator-prompt phrasing ("8k, trending on artstation"), implausible scenes, and metadata that contradicts itself.

These are combined 0.60 / 0.40 with the same vote rule, and use the image label variants above. Appeals, the audit log, rate limiting, and analytics all work for both content types.

### 3. Provenance certificate ("Verified Human Creator")

A creator earns the credential through a live writing check. It applies to the creator, not to a single piece.

1. `POST /certificate/challenge` with `creator_id` returns a random personal prompt (for example "Describe the last piece you wrote: where you were, what was hard about it, and what you changed"), a 60-word minimum, and a 10-minute expiry.
2. `POST /certificate/verify` with the `challenge_id`, `creator_id`, and `response` runs the response through the full three-signal text pipeline. It passes if the score is below 0.40 and no signal votes `ai`. Each challenge can be used once; wrong creator returns 403, reuse 409, expiry 410.
3. On a pass, a certificate is issued with a 180-day expiry and an HMAC-SHA256 signature over its fields. The key comes from `CERT_SECRET`, or is generated once into `.cert_secret` (gitignored).
4. `GET /certificate/<id>` recomputes the signature and checks expiry. A record edited directly in the database shows `valid: false`, and the badge disappears from that creator's content.

The badge appears as `creator_verification` on `/submit`, `/content/<id>`, and the reviewer queue. It is shown **alongside** the label and never changes the score. A verified human can still publish AI text, and the badge text says so.

Tested: a casual personal response passed (score 0.17, all three signals voted human). An AI-style response failed (score 0.81, LLM and stylometry voted AI). Each outcome is logged as `certificate_issued` or `certificate_failed`.

### 4. Analytics dashboard

`GET /dashboard` is a self-contained HTML page (inline CSS bar charts, light and dark mode, no external assets). `GET /analytics` returns the same data as JSON. Both are computed from the database on every request.

- **Detection patterns:** count and share per attribution, overall and per content type; average score overall and per signal; average confidence per attribution.
- **Appeal rate:** overall, and per original attribution. Appeals concentrated on "likely AI" results would suggest false positives.
- **Signal agreement rate (additional metric):** share of classifications with no signal conflict, plus how often each adjustment fires. A falling agreement rate on real traffic means the signals are diverging and the weights need review.
- **Certificates:** issued, failed, and pass rate.

## Known Limitations

- **Formal and academic human writing is pushed toward the AI band.** The monetary-policy sample scored 0.73. Academic prose has long words (stylometry's word-length sub-score was 1.00), evenly sized sentences (burstiness 0.99), and no personal voice (voice 0.75). The LLM also reads the impersonal register as AI-like (0.78). All three signals make the same mistake for related reasons, so they agree and no conflict rule triggers. Only the 0.80 threshold keeps it from being labeled AI; a slightly more formal paragraph would cross it. Students, researchers, and legal writers are the creators most likely to be wrongly flagged, and they are also the most likely to fail the certificate check.
- **Poetry with even line lengths.** Line breaks count as sentences, so a poem with regular meter gets a burstiness sub-score of 1.00 (the test poem did). It is saved here by first-person voice, short everyday words, and the 40-word cap. A longer, formal, third-person poem would have none of those protections.
- **AI text prompted to sound casual or personal is missed.** First person, contractions, short words, and varied sentences fool the stylometry and voice signals at once. The lightly edited AI sample scored 0.38. The system is tuned to avoid false accusations, so it accepts these misses.
- **Results near a threshold can flip between runs.** The LLM is not fully deterministic even at temperature 0. The work-life sample landed exactly on 0.80 in one run, and the same AI paragraph scored 0.88 in one run and 0.81 in another.
- **Image metadata is easy to strip or forge.** Social platforms and screenshots remove camera data, and anyone can edit the software tag. A generator tag is strong evidence when present, but its absence proves little.
- **The certificate can be gamed.** Someone can paste AI-written text that has been made casual into the challenge. The 10-minute window, personal prompt, and 3-per-hour limit make this harder, not impossible.
- **Non-native English writers.** Simple structure and textbook transitions ("Furthermore", "In conclusion") are what the LLM and the marker list look for.
- **AI-assisted human writing** (Grammarly, rewording tools) cannot be told apart from AI-generated writing.
- **Small calibration set.** 7 text and 4 image samples show the scores move in the right direction. They do not make the scores calibrated probabilities.
- **Operational:**
  - Rate limits are kept in memory, so they reset on restart, and they are per-IP, so users behind one NAT share a limit.
  - There is no authentication, and `/log` and `/dashboard` are open for grading visibility.
  - Lists, code, and heavily formatted text break sentence splitting.

## What I Would Change for a Real Deployment

- Build a labeled corpus of hundreds of samples per genre and fit a calibration step (for example isotonic regression) so that a 0.8 actually means about 80%. Fit the ensemble weights on that data instead of choosing them by hand.
- Add a perplexity-based signal from an open-weight model, which measures token predictability directly.
- Use per-genre thresholds, so poetry and academic writing are not compared against blog-post norms.
- For images, analyze the pixels (C2PA content credentials, generator watermarks, a trained image classifier) instead of relying on metadata.
- Add authentication for creators and reviewers, a reviewer endpoint to resolve appeals, and access control on `/log` and `/dashboard`.
- Use Redis-backed rate limits keyed on the authenticated account rather than IP.

## Spec Reflection

**How the spec helped:** Writing the scoring rules in `planning.md` as exact formulas, with hand-calculated example cases in the AI Tool Plan, gave me a test before the code existed. The generated scoring function was checked against those cases immediately, both for the two-signal version and the three-signal ensemble. When the calibration later failed, I could rule out the scoring logic and look at the signals instead. The fixed API contract also meant `/submit`, the audit log, and `/appeal` connected without rework across milestones, and the stretch features plugged into the same scorer, labels, and audit log.

**Where the implementation diverged:** The spec defined Signal 2 as burstiness, lexical diversity (MATTR), and trigram repetition. Calibration showed two of the three carried no information at the 30-60 word lengths users actually submit, and repetition actively mislabeled the poem it was meant to protect. I replaced them with word length and AI marker vocabulary after measuring candidates on the same samples, lowered the short-text cap from 80 to 40 words, and recorded the before/after in `planning.md` (Section 3, Calibration revision). When I added the third signal, I replaced the spec's two-signal "gap greater than 0.4" disagreement rule with a vote-conflict rule, which generalizes to any number of signals. Smaller divergences came from matching the course's test commands:
- the appeal field became `creator_reasoning`;
- `creator_id` became optional on appeals;
- the minimum length dropped to 10 words;
- success responses use `200` rather than `201`.

## AI Usage

I used Claude Code throughout, giving it sections of `planning.md` plus the architecture diagram as context for each milestone.

1. **Stylometric signal (Milestone 4).** I directed it to implement Signal 2 exactly as specified: burstiness, MATTR lexical diversity, and trigram repetition with the mappings from the spec table. It produced a correct implementation of that spec, but running the calibration script put every sample in the uncertain band. I had it print each sub-score separately, which showed two sub-metrics stuck at 0.00. I then had it measure six candidate replacement metrics on the same samples, chose word length and AI marker vocabulary based on those numbers, and overrode the spec's 80-word cap and the LLM prompt's "stay near 0.5" instruction.
2. **Appeals endpoint (Milestone 5).** I directed it to build `/appeal`, label generation, and rate limiting from the spec sections. Before generating code, it compared the spec's API contract against the course's provided test commands and flagged four conflicts:
   - the spec named the field `reasoning`, but the provided curl sends `creator_reasoning`;
   - the spec required `creator_id`, but the provided curl doesn't send one;
   - the spec returned `201` where the tests expect `200`;
   - the provided 11-word rate-limit test text was below the spec's 20-word minimum, so it would have returned `400` instead of demonstrating the limit.

   I had it implement the course contract, lower the minimum to 10 words (safe because texts under 40 words are always capped to uncertain), and update `planning.md` to match. I then verified every error path (400, 403, 404, 409, 429) against the running server.
3. **Stretch features.** I had it measure candidate "personal voice" features on the labeled samples before choosing the third signal, and write all four stretch specs into `planning.md` before any code. Two of its own spec examples were wrong: its hand-calculated ensemble cases had rounding errors (0.90 where the formula gives 0.89), and two cases sat exactly on a rounding boundary that would make fragile tests. I had them recomputed and replaced before they were used as tests. Its first metadata check matched generator names as substrings, so "influx" matched "flux" and "imagenet" matched "imagen"; I had it switch to whole-word matching and verified both cases.
4. **Smaller corrections during review.**
   - A generated docstring in the Milestone 3 placeholder scorer claimed the score was clamped when the code did not clamp it. It was corrected to describe what the code does.
   - A first draft of the reviewer-queue query joined two tables with `SELECT c.*`, which produced duplicate column names. It was rewritten as a lookup per appeal.
   - When every request to port 5000 returned `403`, the cause turned out to be the macOS AirPlay Receiver, and the default port was moved to 5001.
