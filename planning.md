# Provenance Guard - Planning Spec

Provenance Guard is a Flask API that takes a piece of text (poem, story excerpt, blog post), estimates whether it was written by a human or generated by AI, attaches a plain-language transparency label, logs every decision, and lets creators appeal a classification.

Stack: Python 3, Flask, Flask-Limiter, Groq API (`openai/gpt-oss-120b`), SQLite (stdlib `sqlite3`), python-dotenv.

This document is the implementation spec. Sections are referenced by name in the AI Tool Plan.

---

## 1. System Overview

### Submission path (text to label)

1. **API layer (`POST /submit`)** - Accepts JSON `{ "text", "creator_id" }`. Rate limiter checks the caller's IP. Validator rejects missing/non-string fields and text outside 10 to 5000 words. Generates a `content_id` (UUID4).
2. **Signal 1: LLM classifier** - Sends the raw text to Groq and gets back an AI probability and a one-sentence reason.
3. **Signal 2: Stylometric analyzer** - Measures sentence-length variation, average word length, and AI marker vocabulary locally and turns them into an AI probability.
4. **Confidence scorer** - Combines both signal scores into one `ai_score`, applies uncertainty adjustments, and assigns an attribution category.
5. **Label generator** - Picks one of three fixed label texts based on the category.
6. **Storage + audit log** - Saves the content record (status `classified`) and appends a `classification` audit entry.
7. **Response** - Returns the decision record including the label text.

### Appeal path

1. **API layer (`POST /appeal`)** - Accepts `{ "content_id", "creator_reasoning", "creator_id" (optional) }`. Validates existence, ownership if `creator_id` is given, and state.
2. **Status update** - Content status `classified` -> `under_review`. Original decision is never modified.
3. **Audit log** - Appends an `appeal` entry containing the reasoning and the original decision.
4. **Response** - Returns the appeal record.

### Components and files

| Component | File | Responsibility |
|---|---|---|
| API layer + rate limiter | `app.py` | Routes, validation, error responses, Flask-Limiter config |
| Signal 1 | `detection/llm_signal.py` | `llm_signal(text) -> dict` |
| Signal 2 | `detection/stylometry.py` | `stylometry_signal(text) -> dict` |
| Confidence scorer | `detection/scoring.py` | `combine(llm, stylo, word_count) -> dict` |
| Label generator | `labels.py` | `make_label(attribution, ai_score) -> str` |
| Storage + audit log | `storage.py` | SQLite tables `content`, `appeals`, `audit_log` |

## 2. Detection Signals

Both signals output a dict with an `ai_probability` float in [0.0, 1.0] where 0.0 = certainly human and 1.0 = certainly AI. Neither outputs a binary flag.

### Signal 1: LLM Classifier (Groq `openai/gpt-oss-120b`)

**Measures:** Holistic style and content judgment: generic or hedged phrasing, formulaic structure (intro / three points / conclusion), lack of concrete personal detail, emotional flatness, and common AI vocabulary ("delve", "tapestry", "it is important to note").

**Why it differs:** A large model has seen huge volumes of both human and machine text and can recognize high-level patterns that simple statistics cannot.

**Blind spots:** Uncalibrated (its probabilities are opinions, not measured frequencies). Biased against formal, simple, or non-native English writing. Fooled by lightly edited AI text. Non-deterministic and depends on an external service.

**Implementation:**
- Call: `client.chat.completions.create(model="openai/gpt-oss-120b", temperature=0, response_format={"type": "json_object"}, ...)`.
- System prompt instructs the model to act as an AI-text detector and return only JSON `{"ai_probability": <float 0-1>, "reasoning": "<one sentence>"}`, and gives an explicit calibration scale (0.85-0.95 for several strong AI markers, 0.40-0.60 for mixed evidence, 0.05-0.15 for clear human traits) so it uses the full range instead of hedging toward the middle.
- Text sent truncated to the first 3000 words.
- Raw value clamped to [0.02, 0.98]; the model is never allowed to claim certainty.
- On API error, timeout (15s), or invalid JSON: return `status: "unavailable"` and `ai_probability: null`. The request still succeeds.

**Output:**
```json
{ "ai_probability": 0.82, "reasoning": "Uniform structure and generic transitions.", "status": "ok" }
```

### Signal 2: Stylometric Analyzer (local, pure Python)

**Measures:** Three statistics, each mapped to a 0-1 sub-score (higher = more AI-like), then averaged equally.

| Sub-metric | Raw measure | Mapping to 0-1 (initial values, tuned in M4) |
|---|---|---|
| Burstiness | Coefficient of variation (stdev / mean) of sentence lengths in words | CV <= 0.25 -> 1.0; CV >= 0.75 -> 0.0; linear in between |
| Word length | Mean letters per word | mean <= 4.2 -> 0.0; mean >= 5.8 -> 1.0; linear in between |
| AI marker vocabulary | Fraction of words in a fixed list of stock AI words ("furthermore", "stakeholders", "ensure", "transformative", "delve", ...; full list in `stylometry.py`) | `min(1, rate / 0.05)` |

Sentences split on `.`, `!`, `?`, and line breaks (so poetry lines count as units). Words are lowercase alphabetic tokens.

**Why it differs:** Language models choose high-probability tokens, producing evenly sized sentences in a polished, formal register with longer Latinate words and a recognizable set of stock transitions. Humans mix long and short sentences, use fragments, short everyday words, and casual phrasing.

**Blind spots:** Weak on very short text (too few sentences for variance). Poetry has even line lengths, so burstiness reads AI-like. Formal or academic human writing has long words and uniform sentences, so it scores mid-high. The marker list is easy to evade by avoiding those words, and AI text prompted to sound casual passes. Cannot see meaning at all.

**Output:**
```json
{
  "ai_probability": 0.61,
  "burstiness": 0.74, "word_length": 1.0, "ai_markers": 1.0,
  "raw": { "sentence_length_cv": 0.379, "mean_word_length": 6.23, "marker_rate": 0.186 },
  "sentence_count": 3, "word_count": 43, "status": "ok"
}
```

### Why these two

They fail in different ways. The LLM reads meaning but is opaque and uncalibrated; stylometry is transparent, deterministic, and free but blind to content. Agreement between them is real evidence; disagreement is treated as uncertainty.

### Combining into one score

> Superseded by the three-signal ensemble in Stretch S1 (weights 0.45 / 0.35 / 0.20 plus a vote-conflict rule). The two-signal version below is kept as the original Milestone 4 design.

```
ai_score = 0.6 * llm.ai_probability + 0.4 * stylometry.ai_probability
```

The LLM gets more weight because it captures content-level patterns. Stylometry has enough weight to pull a borderline case into the uncertain band. Adjustments are in Section 3.

## 3. Uncertainty Representation

### What the score means

`ai_score` is the system's estimate of how likely the text is AI-generated, in [0.0, 1.0].

- **0.6 means:** the evidence leans slightly toward AI but is not strong enough to tell a reader so. It is reported as "Origin unclear." A 0.6 is not "60% AI content" and not a verdict.
- **0.95 means:** both signals agree strongly; the system will label the text as likely AI.
- **0.5 means:** no usable evidence either way.

`confidence = max(ai_score, 1 - ai_score)`: how strongly the score leans to whichever side it is on. Returned alongside `ai_score` so a client does not need to interpret direction.

### Mapping raw signal outputs to a calibrated score

> Rule 2 (disagreement gap > 0.4) was replaced by the vote-conflict rule in Stretch S1. Rules 3-5 still apply.

Applied in this order in `scoring.py`:

1. **Weighted average** (Section 2).
2. **Disagreement penalty:** if `abs(llm - stylo) > 0.4`, shrink toward 0.5 by half: `ai_score = 0.5 + (ai_score - 0.5) * 0.5`. Adds `"signal_disagreement"` to `adjustments`.
3. **Short-text cap:** if `word_count < 40`, clamp to [0.30, 0.70]. Adds `"short_text_cap"`.
4. **Signal failure:** if the LLM is unavailable, `ai_score = stylo` clamped to [0.30, 0.70]. Adds `"llm_unavailable"`.
5. Round to 2 decimals.

Calibration check: run the labeled set in `tests/samples.py` with `python -m tests.run_calibration`. Target: clear AI samples >= 0.80, clear human samples < 0.30, borderline cases in the uncertain band, and zero human samples >= 0.80. If a human sample crosses 0.80, raise the AI threshold or lower the LLM weight before changing anything else.

### Calibration revision (Milestone 4)

The first implementation (v1) put all 7 test samples in the uncertain band:

| Sample | Truth | v1 LLM | v1 stylo | v1 score | v2 LLM | v2 stylo | v2 score | v2 attribution |
|---|---|---|---|---|---|---|---|---|
| clear_ai | AI | 0.78 | 0.25 | 0.53 | 0.88 | 0.91 | 0.89 | likely_ai |
| ai_worklife | AI | 0.78 | 0.31 | 0.55 | 0.78 | 0.93 | 0.84 | likely_ai |
| borderline_edited_ai | AI | 0.35 | 0.25 | 0.31 | 0.22 | 0.45 | 0.31 | uncertain |
| borderline_formal_human | human | 0.62 | 0.33 | 0.50 | 0.78 | 0.66 | 0.73 | uncertain |
| clear_human | human | 0.15 | 0.09 | 0.30 | 0.09 | 0.11 | 0.10 | likely_human |
| human_bike | human | 0.15 | 0.03 | 0.30 | 0.09 | 0.03 | 0.07 | likely_human |
| human_poem | human | 0.22 | 0.76 | 0.47 | 0.09 | 0.33 | 0.30 | uncertain (short_text_cap) |

Causes found by printing each sub-metric separately, and the changes made:

1. **Lexical diversity (MATTR) scored 0.00 on every sample.** At 30-60 words, type-token ratio is 0.86-0.90 for both human and AI text, so it carried no information. Replaced with mean word length, which measured 5.2-6.2 for AI samples and 3.8-4.3 for casual human samples.
2. **Repetition scored 0.00 on everything except the poem, where the refrain pushed it to 1.00.** It only produced a false AI signal on the case it was supposed to protect. Replaced with AI marker vocabulary, which was 0.055-0.186 on two AI samples and 0.0 on all human samples.
3. **The LLM hedged** (0.78 on textbook AI text) because the prompt told it to stay near 0.5. Added an explicit calibration scale to the prompt.
4. **The 80-word short-text cap covered every test input** (32-55 words), so no text could ever get a confident label. Lowered to 40 words: still covers haiku and short poems, but allows typical paragraph-length submissions to be classified.

Remaining known weakness: formal human writing (0.73) sits near the AI threshold. Both signals read academic register as AI-like. The asymmetric 0.80 threshold is what keeps it uncertain.

### Thresholds

| `ai_score` | Attribution | Label variant |
|---|---|---|
| 0.80 - 1.00 | `likely_ai` | High-confidence AI |
| 0.30 - 0.79 | `uncertain` | Uncertain |
| 0.00 - 0.29 | `likely_human` | High-confidence human |

Asymmetric on purpose: wrongly labeling a human as AI is the more harmful error, so the AI band is narrower (top 20%) than the human band (bottom 30%), and the uncertain band is the widest. Example: 0.51 -> uncertain, 0.95 -> likely AI, 0.15 -> likely human.

## 4. Transparency Labels

Exact text shown to readers. `{pct}` is a whole-number percentage: `round(ai_score * 100)` for the AI label, `round((1 - ai_score) * 100)` for the human label.

| Variant | Condition | Label text |
|---|---|---|
| High-confidence AI | `ai_score >= 0.80` | "Likely AI-generated. Our analysis found strong signs that this text was written by an AI tool (estimated {pct}% likelihood). This is an automated estimate, not a final judgment. The creator can appeal this result." |
| High-confidence human | `ai_score < 0.30` | "Likely human-written. Our analysis found strong signs that this text was written by a person (estimated {pct}% likelihood). This is an automated estimate, not a guarantee." |
| Uncertain | `0.30 <= ai_score < 0.80` | "Origin unclear. Our analysis could not confidently tell whether this text was written by a person or an AI tool. Treat this result as inconclusive. The creator can appeal this result." |

Design choices:
- The first two words state the result, so a skimming reader gets it immediately.
- Percentages appear only in the confident labels. Showing "54%" on an uncertain result would suggest precision the system does not have.
- Every label says the result is an automated estimate. The AI and uncertain labels mention appeals, since those are the ones a creator would contest.
- No technical terms (no "signal", "score", "classifier").

When content is `under_review`, the response adds `review_notice`: "The creator has appealed this result. It is under human review."

## 5. Appeals Workflow

### Who can appeal

The original creator. If the appeal includes `creator_id`, it must match the `creator_id` stored at submission (403 otherwise). `creator_id` is optional on appeals so that holding the `content_id` (returned only to the submitter) is enough to appeal; there is no authentication system in this project, so this is an identifier check, not a security boundary. Any attribution can be appealed, including `likely_human` (e.g., a creator who used AI and wants an accurate label).

### What they provide

```json
{ "content_id": "uuid", "creator_reasoning": "string, 20-2000 chars", "creator_id": "string, optional" }
```

### What the system does

1. Validate: reasoning length (400), content exists (404), creator matches if provided (403), status is `classified` (409 if already `under_review`).
2. Insert an `appeals` row: `appeal_id`, `content_id`, `creator_id`, `reasoning`, `status: "pending"`, `created_at`.
3. Update `content.status` to `under_review`. Scores and label stay unchanged.
4. Append audit entry `event: "appeal"` with the reasoning and a copy of the original decision (attribution, ai_score, both signal scores, label).
5. Return `200` with a confirmation message and the appeal record. Steps 2-4 run in one SQLite transaction, and the status update only succeeds if the content is still `classified`, so two simultaneous appeals cannot both be accepted.

No automated re-classification.

### What a reviewer sees

`GET /appeals?status=pending` returns the queue, oldest first. Each item:

```json
{
  "appeal_id": "uuid",
  "submitted_at": "ISO-8601",
  "creator_id": "string",
  "reasoning": "This is my original poem; the refrain is intentional.",
  "content": { "content_id": "uuid", "text_excerpt": "first 300 chars...", "word_count": 60 },
  "original_decision": {
    "attribution": "uncertain", "ai_score": 0.70, "confidence": 0.70,
    "signals": { "llm": 0.75, "stylometry": 0.70 },
    "llm_reasoning": "Polished imagery and regular structure.",
    "adjustments": ["short_text_cap"],
    "label": "Origin unclear. ..."
  }
}
```

The reviewer can see at a glance which signal drove the decision and whether adjustments were applied. Resolving appeals is out of scope.

## 6. Anticipated Edge Cases

Specific content the system will handle poorly, and how each is mitigated:

1. **Repetitive poem with simple vocabulary.** A human poem with a refrain ("I remember the river / I remember the rain") and short, even lines. Even line lengths give it a high burstiness sub-score, and the LLM may read simple imagery as generic. Mitigation: short everyday words keep the word-length sub-score low, poems under 40 words are capped to uncertain, and the 0.80 AI threshold requires both signals to agree strongly. (The original repetition metric scored this exact poem 1.00 and was removed for that reason; see Calibration revision.)
2. **Non-native English writer.** A blog post with simple sentence structure, limited vocabulary, and textbook transitions ("Firstly", "In conclusion"). The LLM is known to over-flag this style, and textbook transitions may hit the AI marker list. Mitigation: if stylometry disagrees by more than 0.4, the score is pulled toward 0.5; the appeal record shows the per-signal split so a reviewer can see the LLM alone drove it.
3. **Human text polished with Grammarly or similar tools.** Smoothed phrasing lowers burstiness and removes the irregularities stylometry relies on. Neither signal can tell "AI-written" from "AI-edited". Mitigation: the label says "automated estimate" and the appeal reasoning lets the creator explain.
4. **AI text edited by a human.** Sentence lengths varied by hand and personal details added. Stylometry reads human and the LLM may as well. This is a false negative the system accepts; the asymmetric thresholds prioritize avoiding false accusations over catching every AI text.
5. **Very short submissions (10-39 words), such as haiku or a single paragraph.** Too little data for either signal. Always capped to uncertain.
6. **Lists, code, or heavily formatted text.** Bullet lists break sentence splitting (no terminal punctuation, many one-word "sentences"), inflating burstiness. Out of scope; the README notes the system is designed for prose and poetry.

## 8. Rate Limiting

Flask-Limiter, keyed on remote IP, in-memory storage. Limits are constants at the top of `app.py`.

| Endpoint | Limit | Reasoning |
|---|---|---|
| `POST /submit` | 10 per minute; 100 per day | Each submission costs one Groq call, and Groq's free tier caps the whole key at roughly 30 requests/minute. 10/min per client leaves headroom for several users. 100/day stops bulk scraping and people probing the detector to learn how to evade it, while staying well above what a real creator submits. |
| `POST /appeal` | 5 per hour | Each appeal costs human review time. A creator rarely needs more than one appeal per piece; 5/hour covers several pieces without letting one client flood the queue. |
| `GET` endpoints | 60 per minute | Cheap reads; limited only to prevent abuse. |

Exceeding a limit returns `429` with `{ "error": "rate_limited", "message": "..." }`.

## Architecture

The submission flow takes raw text through validation, two independent detection signals, a scorer that turns their outputs into one calibrated `ai_score`, and a label generator, then records the full decision in the audit log before responding. The appeal flow lets the original creator contest a decision: it changes the content's status to `under_review` and logs the creator's reasoning next to an unchanged copy of the original decision, so a human reviewer has everything in one place. Neither flow ever deletes or overwrites a past decision.

### Submission flow

> Since Stretch S1/S2, the text path runs a third signal (personal voice) before the scorer, and image submissions run metadata forensics plus an LLM consistency check. See the README architecture section for the current flow.

   v
+-------------------+
| Signal 1: LLM     |  Groq openai/gpt-oss-120b, temperature 0
| classifier        |
+-------------------+
   |
   | raw text + llm ai_probability (0-1) + reasoning

+-------------------+
| Signal 2:         |  burstiness, word length, AI marker vocabulary

+-------------------+
   |
   | llm score + stylometry score + word_count

## Stretch Features

Status: all four implemented and tested; results recorded in the README.

Specs written before implementation. Order: S1 ensemble (changes the scorer the others depend on), S2 multi-modal, S3 provenance certificate, S4 analytics dashboard.

### S1. Ensemble Detection (3 signals, weighted vote)

**Signal 3: Personal voice analyzer** (`detection/voice.py`, local). Measures evidence that a specific person is talking, which neither existing signal measures directly:

| Sub-metric | Raw measure | Mapping to human-evidence 0-1 |
|---|---|---|
| First person | Rate of i/me/my/mine/myself/i'm/i've/i'd/i'll per word | `min(1, rate / 0.06)` |
| Informal markers | Rate of contractions + casual punctuation (`?`, `!`, `...`, dashes, parentheses) + all-caps emphasis words + digits, per word | `min(1, rate / 0.04)` |
| Lowercase starts | Fraction of sentences starting with a lowercase letter | as is |

`human_evidence = mean of the three`; `ai_probability = 0.75 * (1 - human_evidence)`.

The 0.75 ceiling is deliberate: missing personal voice is weak evidence of AI (formal human writing has none either), while present personal voice is strong evidence of a human. The signal can pull a score toward human strongly but toward AI only mildly.

Measured on the labeled samples before choosing it: first-person rate was 0.000 on all AI samples except the edited one (0.026) and 0.073-0.188 on casual human samples; lowercase starts were 0.00 on every AI sample.

**Blind spots:** AI text prompted to write in first person with contractions (the edited AI sample) reads as human. Formal human writing gets no credit. Poetry in second or third person gets no credit.

**Combining (weighted average + vote check):**

```
text:  ai_score = 0.45 * llm + 0.35 * stylometry + 0.20 * voice
```

Weights reflect measured separation on the samples: the LLM reads content and leads; stylometry separated the samples well in M4; voice gets the smallest weight because it is one-sided by design.

Each signal also casts a vote: `ai` if its probability >= 0.60, `human` if <= 0.40, otherwise `abstain`. Votes are returned in the response and logged.

Adjustments (replace the two-signal rules in Section 3; applied in order):
1. **Signal conflict:** if at least one signal votes `ai` and another votes `human`, shrink toward 0.5 by half. A confident label therefore requires no signal to actively contradict it. Adjustment `signal_conflict`.
2. **Short-text cap:** under 40 words, clamp to [0.30, 0.70] (unchanged).
3. **Unavailable signal:** remaining weights are renormalized and the score is clamped to [0.30, 0.70]. Adjustment `<signal>_unavailable`.

Hand-calculated checks: (llm 0.95, stylo 0.90, voice 0.75, 200 words) -> 0.4275 + 0.315 + 0.15 = 0.89 `likely_ai`; (0.10, 0.10, 0.00, 200 words) -> 0.08 `likely_human`; (0.90, 0.10, 0.30, 200 words) -> votes ai/human/human -> raw 0.50 -> conflict -> 0.50 `uncertain`; (0.75, 0.70, 0.75, 30 words) -> 0.73 -> capped 0.70 `uncertain`.

### S2. Multi-modal Support (images via metadata + description)

`POST /submit` accepts `content_type: "image"` (default `"text"`). The image itself is not uploaded; the platform submits what it already has for an image: its embedded metadata and the creator's description.

```json
{
  "content_type": "image",
  "creator_id": "string",
  "description": "string, optional, max 2000 chars",
  "metadata": {
    "width": 1024, "height": 1024,
    "software": "string", "make": "string", "model": "string",
    "exposure_time": "1/250", "f_number": 2.8, "iso": 200, "focal_length": 35,
    "gps": true, "digital_source_type": "string"
  }
}
```

At least one of `metadata` (non-empty object) or `description` is required. Unknown metadata keys are kept and their string values are scanned for generator names.

**Image signal 1: Metadata forensics** (`detection/image_metadata.py`, rule-based):
- Generator evidence: any string value containing a known AI generator name (midjourney, dall-e, dalle, stable diffusion, sdxl, comfyui, automatic1111, firefly, imagen, leonardo, ideogram, flux, novelai) or `digital_source_type` of `trainedAlgorithmicMedia` / `compositeWithTrainedAlgorithmicMedia` -> 0.95.
- Otherwise start at 0.50, subtract 0.08 per camera field present (make, model, exposure_time, f_number, iso, focal_length, gps), add 0.15 if both dimensions are common generator sizes (512, 640, 768, 832, 896, 1024, 1152, 1216, 1344, 1536, 1792, 2048), add 0.10 if no camera fields at all. Clamp to [0.05, 0.95].
- Blind spot: social platforms and screenshots strip metadata, and metadata is trivially editable. Absence of camera data is therefore only mild evidence.

**Image signal 2: LLM consistency check** (`llm_image_signal` in `detection/llm_signal.py`): gpt-oss-120b judges the description and metadata together: whether the described scene is physically plausible, whether the description uses generator-prompt phrasing ("hyperrealistic, 8k, trending on artstation"), and whether metadata fields contradict each other (a phone camera model at 1024x1024). Same JSON contract and clamping as Signal 1.

**Combining:** `ai_score = 0.60 * metadata + 0.40 * llm`. Metadata leads because it is direct evidence about the file; the LLM only sees text about the image. Same vote/conflict rule and unavailable-signal rule as S1. If metadata has no recognized fields and no description is given, clamp to [0.30, 0.70] (`insufficient_evidence`). No short-text cap.

**Image labels** (same thresholds, wording adapted):

| Variant | Label text |
|---|---|
| High-confidence AI | "Likely AI-generated. Our analysis found strong signs that this image was created with an AI tool (estimated {pct}% likelihood). This is an automated estimate, not a final judgment. The creator can appeal this result." |
| High-confidence human | "Likely human-made. Our analysis found strong signs that this image was captured or created by a person (estimated {pct}% likelihood). This is an automated estimate, not a guarantee." |
| Uncertain | "Origin unclear. Our analysis could not confidently tell whether this image was made by a person or an AI tool. Treat this result as inconclusive. The creator can appeal this result." |

Appeals, audit log, and rate limits work identically for both content types; `content_type` is stored and logged.

### S3. Provenance Certificate ("Verified Human Creator")

A credential earned by a **creator** (not a single piece) through a live writing check, displayed next to the label on all their content. It never changes a piece's score or label.

**Flow:**
1. `POST /certificate/challenge` `{ "creator_id" }` -> `{ "challenge_id", "prompt", "min_words": 60, "expires_at" }`. The prompt is picked at random from a fixed list of personal questions (e.g., "Describe the last piece you wrote: where you were, what was hard, and what you changed."). Expires in 10 minutes. Limit: 3 per hour.
2. `POST /certificate/verify` `{ "challenge_id", "creator_id", "response" }`. Checks, in order: challenge exists (404), belongs to this creator (403), not used (409), not expired (410), response at least 60 words (400). The challenge is marked used even on failure.
3. The response runs through the full text pipeline (all three signals). **Pass if `ai_score < 0.40` and no signal votes `ai`.**
4. On pass, a certificate is issued: `certificate_id`, `creator_id`, `issued_at`, `expires_at` (180 days), `verification_score`, and `signature = HMAC-SHA256(secret, "certificate_id|creator_id|issued_at|expires_at")`. The secret comes from `CERT_SECRET` in the environment, or is generated once and stored in `.cert_secret` (gitignored).
5. Audit log events: `certificate_issued` or `certificate_failed`, with the verification score and signal scores.

**Checking a certificate:** `GET /certificate/<certificate_id>` returns the certificate and `valid: true|false`, recomputing the signature and checking expiry. A tampered or expired record shows `valid: false`.

**Display:** `/submit` and `/content/<id>` responses include `creator_verification`. For a verified creator:

> "Verified Human Creator. This creator passed a live writing check on {date}. This confirms they write in their own voice; it does not certify that this specific piece was written without AI."

For others: `{ "verified": false }` and no badge text.

**Why it does not override the label:** a verified human can still publish AI text. Showing both lets the reader weigh them.

**Limitations:** someone can paste AI text into the challenge (the 10-minute window and personal prompt make this harder, not impossible); formal writers may fail the check for the same reason they are pushed toward AI in detection (they can request a new challenge, up to 3 per hour).

### S4. Analytics Dashboard

`GET /analytics` returns JSON; `GET /dashboard` renders the same data as a self-contained HTML page (inline CSS bar charts, no external assets, light and dark mode).

Metrics:
- **Detection patterns:** count and percentage per attribution, overall and per content type; average `ai_score`; average score per signal.
- **Appeal rate:** appeals / classifications, overall and per original attribution (shows whether appeals concentrate on AI labels, which would suggest false positives).
- **Signal agreement rate (additional metric):** share of classifications where no signal conflict occurred, and frequency of each adjustment (`signal_conflict`, `short_text_cap`, unavailable signals). A falling agreement rate means the signals are diverging on real traffic and the weights need review.
- **Certificates:** issued, failed, and pass rate.
- Average confidence per attribution.

Computed from the `content`, `appeals`, `certificates`, and `audit_log` tables on each request. Rate limited at the read limit (60/min).
